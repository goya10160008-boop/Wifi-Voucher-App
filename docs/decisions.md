# Decisions

The 20 design decisions are in `docs/superpowers/specs/2026-10-25-voucher-manager-design.md` section 8. This file logs decisions made while building.

## 2026-10-25

1. **Omada PDFs have no text layer.** The sample (`samples/3HRS_10202026.pdf`) is a browser "print to PDF" whose glyphs are outlined vector paths, so `pdfjs-dist` `getTextContent()` returns nothing. `lib/pdf-text.ts` tries the text layer first, then renders each page and runs OCR (`tesseract.js`, digits only, 2x scale). On the sample it read all 56 codes correctly. The preview/untick step stays the safety net. Paste/CSV also works.
2. **OCR assets are self-hosted.** `scripts/copy-ocr.mjs` (runs on `predev` and `prebuild`) copies the tesseract worker, the three `-lstm` core builds, `eng.traineddata.gz` and the pdf.js worker into `public/` (git-ignored). No CDN at runtime. They are static assets, so they do not count toward the 3 MiB Worker limit.
3. **Code format:** `parseCodes` accepts only 6 to 10 digit numeric tokens (confirmed from the sample: 6 digits). The DB regex stays wider (`[A-Za-z0-9-]{4,32}`). If Omada ever issues alphanumeric codes, widen `lib/parse-codes.ts` and add a fixture.
4. **No real-PDF text fixture.** The spec asked for a parse test on real Omada PDF text. There is no text, and the sample holds real unsold codes (git-ignored). `tests/unit/parse-codes.test.ts` uses synthetic OCR-shaped text. The real sample is covered by the Playwright test (needs login).
5. **Hours, not minutes, in the plan form.** Stored as `duration_minutes`. Fractions work (0.5 h = 30 min).
6. **Icons are generated** by `scripts/make-icons.mjs` (see decision 15 for the current A&B mark).
7. **Local DB tests not run.** No Docker on the dev machine. The RPC logic was checked on the remote project inside a transaction that always rolls back (FIFO, idempotent retry, insufficient cash, out of stock, import counts, void burns code, Manila 23:59/00:01 buckets all passed). **Not tested:** true parallel `SKIP LOCKED` (needs two connections). Test it before relying on two sellers at once.
8. **Worker size:** about 2.47 MiB gzipped on 2026-10-25 against the 3 MiB free limit. Watch it when adding dependencies. Server code must not import `pdfjs-dist`, `tesseract.js` or `qrcode.react`.
9. **`proxy.ts` works under OpenNext** (`x-proxy: 1` seen in `npm run preview`), so no `middleware.ts` fallback is needed.
10. **Generated DB types** live in `lib/supabase/database.types.ts` (hand-trimmed from the generator). Regenerate after every migration.

## 2026-10-25: Mint redesign

11. **Design = "Mint"** (chosen by the owner from 5 samples). All colors, radii, shadows and fonts are tokens in `app/globals.css` (`@theme`). Pages use the shared classes (`.btn`, `.btn-ghost`, `.btn-danger`, `.field`, `.card`, `.alert-*`, `.tile`, `.pick`, `.chip`, `.row-link`, `.skeleton`); do not add per-page colors. Only two literal colors remain, both unavoidable: `themeColor` in `app/layout.tsx` and the QR `fgColor` in `components/VoucherCode.tsx` (keep them equal to `--color-pri` / `--color-ink`).
12. **Fonts** DM Sans + DM Mono via `next/font/google`: downloaded and self-hosted at build time, no font CDN at runtime. The build needs internet once.
13. **Animations are pure CSS** (keyframes in `globals.css`): press scale on buttons/tiles, `.code-card` slide-up, `.pop` for "Copied", `app/(app)/template.tsx` page fade (a template remounts per navigation), `.alert` slide-in, `.btn[aria-busy=true]` spinner (set `aria-busy={pending}` on submit buttons), nav pill slide (`--n`/`--i` CSS vars), `.skeleton` shimmer via `loading.tsx` (`(app)/loading.tsx` generic, `sales/loading.tsx`). A `prefers-reduced-motion` block at the end of the file shortens all of them to ~0. No animation library.
14. **Nav** is a client component (`usePathname`) so the active pill can slide between routes. Icons are inline stroke SVGs, decorative (`aria-hidden`); the text label names the link.
15. **Logo** drawn by `scripts/make-icons.mjs` (white WiFi arcs + "A&B" pixel text on `#166534`, 3x3 supersampling). Maskable icon keeps the mark inside the central 60%. Rerun the script after changing it.
16. **Concurrency tests** `supabase/tests/concurrency.test.ts` (single sells) and `supabase/tests/cart.test.ts` (cart sells; apply 0002 too) (4 cases: 20 parallel sells on 10 codes, 5 parallel same-key calls, voided code never resold under 20 parallel sells, two plans do not block each other) needs a LOCAL DB; skipped when `SUPABASE_TEST_DB_URL` is unset. It inserts and deletes rows with a throwaway owner, so never point it at the production project. **Run locally without Docker** (verified 5/5 runs, 4/4 passing, Postgres 18.4): in a scratch dir `npm i embedded-postgres` (real PG binaries; not a repo dependency), start it with `new EmbeddedPostgres({databaseDir, user:'postgres', password:'postgres', port:54329, persistent:false})`, `initialise()`, `start()`, `createDatabase('voucher_test')`; apply `supabase/tests/local-shim.sql` then `supabase/migrations/0001_init.sql` (unmodified) with any pg client; then `SUPABASE_TEST_DB_URL=postgresql://postgres:postgres@127.0.0.1:54329/voucher_test npx vitest run supabase/tests/concurrency.test.ts`. With Docker: `supabase start`, URL `postgresql://postgres:postgres@127.0.0.1:54322/postgres`. The shim only fakes roles, `auth.users` and `auth.uid()`; it does not prove PostgREST, real RLS-as-`authenticated` behaviour (the test connects as superuser) or Supabase pooler behaviour.
17. **Worker size** after the redesign: 2,614,752 bytes gzipped (about 2.49 MiB of the 3 MiB free limit).
18. **Not visually reviewed:** the logged-in screens (Home, Sell, Sales, Plans, Import, Settings, code screen) have not been looked at in a browser, because no owner login existed in the dev environment. `/login` was checked at phone and desktop width. Review the rest with a real login and report anything off.

## 2026-10-25: Independent review fixes

19. **Review result:** no Critical findings; DB grants/RLS/definer functions verified. Six Important findings fixed in the app (no DB change):
    - Totals and the CSV backup were exposed to the API's 1000-row cap. The export now pages with `.range()`; the Sales grand total comes from month buckets.
    - Query errors were shown as zeros. Home and Sales now throw to the error page; the export returns 500; archive/restore throws on a name clash.
    - E2E login waited for a heading that no longer exists, and the voided-total assertion was a tautology. Both fixed (still skipped without `E2E_EMAIL`/`E2E_PASSWORD`).
    - Lost sell response then plan change: the message now says the sale may already be recorded and links to Sales (the key is deliberately not rotated).
    - Same-key retry on the last code could say "out of stock" while the first call was committing. `sell` re-checks by idempotency key on OUT_OF_STOCK and redirects to that sale.
    - OCR: the text-layer check now needs 3 code-shaped tokens (a header date no longer skips OCR), the worker is always terminated, the render size is clamped, and the preview warns that OCR can misread a digit.
20. **Small fixes:** `isDate` rejects impossible dates (`2026-13-45`) instead of crashing; sales list has an `id` tiebreak; CSV guard covers leading tab/CR, adds BOM and `no-store`; security headers (`frame-ancestors 'none'`, `nosniff`); voided rows say "(voided)".
21. **Deferred (needs a DB migration or the owner):** the `payments` SELECT policy has no `active` check for staff (a deactivated staff user could read their own payment rows until the JWT expires); `plans.sort_order` is unused but harmless; turn on "leaked password protection" and asymmetric JWT keys in the Supabase dashboard; the 12-digit merged-token case in OCR is still dropped silently (the preview count check is the guard).

## 2026-10-25: Multi-voucher (cart) sales

22. **A cart is N ordinary sales rows, not a new "order" table.** Migration `0002_sell_cart.sql` adds `sales.group_id` (= the client's idempotency key) and `sales.seq` (1-based, unique per group; both NULL on old rows, enforced together by a CHECK). Void, totals, history, RLS and the CSV all keep working per code. `sell_cart(p_group_key, p_items jsonb, p_tendered_centavos, name, room)` returns the group's rows. Max 10 vouchers per sale across all plans; the same plan listed twice is merged; codes are assigned plan by plan in plan-id order, FIFO inside a plan, so `seq` is not the on-screen order.
23. **Carts are serialised per plan** with `select ... from plans where id = any(...) order by id for no key update`, taken before stock is counted. Reason: with only `SKIP LOCKED`, two carts each needing 2 of the last 2 codes can each skip the row the other holds and both fail although stock existed, and a cart behind one that rolls back reports a false OUT_OF_STOCK. Locking plans in id order also rules out deadlocks between mixed carts. `NO KEY UPDATE` does not block the foreign-key checks of single `sell_voucher` calls. `SKIP LOCKED` stays on the voucher pick (it still protects against single sells). Local mutation checks (PG 18.4): removing the plan lock fails "a cart waiting behind another cart that rolls back"; removing the existing-group re-check fails the same-key tests; removing all locks fails the parallel carts; LIFO fails the FIFO tests. Removing `SKIP LOCKED` alone does not fail any test: on current Postgres the LIMIT sits above the lock step, so a blocked reader re-scans to the next row. It is a wait-time optimisation, not a correctness need.
24. **Cash is stored once**, on the `seq = 1` payment (`tendered_centavos` = all cash handed over; the check `tendered >= amount` still holds). Change shown = tendered minus the sum of the group's prices (voided rows included, since the guest paid at the original total). One cash payment row per code, as before, so voiding one code voids only its payment.
25. **Idempotency** = the group key. Per-row keys are `md5(group_key || ':' || seq)::uuid`, so a retry returns the same rows (even after stock ran out or a plan was archived) and the same key with different items is `KEY_REUSED` (also if a different user presents the key). The existing-group check runs after the plan locks so a concurrent same-key call waits and then returns the first call's sale instead of OUT_OF_STOCK.
26. **All sales now go through `sell_cart`** (a single voucher is a cart of 1 and still redirects to `/sales/[id]`). `sell_voucher` is untouched and still tested but unused by the app; remove it in a later migration if wanted.
27. **Migration 0002 must be applied to the remote project before the new Sell page works.** Until then the page shows "The database is missing the cart update (migration 0002)". Local `npm run dev` talks to the same remote database.
28. **Found by the new tests:** a cart item with a missing `plan_id` slipped past the shape check (NULL inside `bool_or` is ignored) and failed later as PLAN_NOT_FOUND. Fixed with `coalesce(..., false)`.
29. **Known limits:** the Sales list groups rows within the 50-row page it fetched, so a cart can be split across a page boundary (each row still opens correctly). Item errors for a short plan come back as `OUT_OF_STOCK` with DETAIL "<plan>|<codes left>" and are shown as "Only N codes left for <plan>". The logged-in UI (cart, group page, Copy all) has not been looked at in a browser.
30. **Worker size** after the cart: 2,623,810 bytes gzipped (about 2.50 MiB of the 3 MiB free limit), measured with `npx opennextjs-cloudflare build` from the project root.

## 2026-10-25: Screenshot receipt

31. **Receipt = the same two pages with `?receipt=1`** (`/sales/group/[id]`, `/sales/[id]`), not a new route. `Nav` reads the flag with `useSearchParams` and renders nothing, so the paper is all that shows. Built only from rows the page already loaded: no extra query, no write, no public link, no migration. Staff still see only their own sales through RLS.
32. **The paper fills the first screen, the buttons sit below the fold** (`.receipt-stage` is `100dvh - 2rem` tall). A normal phone screenshot is just the receipt; "Copy receipt as text" and "Done" are one scroll down. "Show receipt" is a normal push navigation, so the browser Back button returns to the sale page; "Done" goes back (or replaces with the sale page if there is no history).
33. **Voided codes never print.** The total and plan lines stay what was paid (so cash and change still add up), but a voided code shows a red VOIDED stamp with no digits, in the page and in the copied text, plus "Voided codes cannot be used." An old screenshot of a receipt cannot be re-copied from the app, but the customer still has the digits from before the void; that is the same residual risk as before and the reason voided codes are burned.
34. **A single code that was sold in a cart gets a receipt for that code only, with no cash or change line.** The cart's cash is stored once, on the first code's payment, so using it against one code's price would show wrong change. The same bug existed in the normal single-sale page (code 1 of a cart showed the whole cart's cash minus one price); fixed there too. The group receipt is the right one for a customer.
35. **Layout:** up to 5 codes use 38px digits, 6 to 10 use 28px (`data-dense`). Measured at 390 px wide with 10 codes (3 plan lines, one voided): paper 805 px tall, which fits an 844 px screen but not a phone with a tall browser bar; then the paper scrolls and the buttons stay below it. Codes are digits only, so no 0/O confusion handling is needed (the mono font draws a slashed zero anyway).
36. **Wording** lives in `lib/receipt.ts` (`BUSINESS_NAME`, instruction line, thanks). No WiFi name or URL is printed because none is known; edit the constants to add them.
37. **Not verified:** the logged-in receipt pages have not been seen in a browser (no owner login). The receipt component was rendered with sample data on a throwaway page (deleted, not committed) and checked at 390x844. The e2e test `receipt: ...` is skipped without `E2E_EMAIL`/`E2E_PASSWORD`.
38. **Worker size** with the receipt: 2,627,342 bytes gzipped (about 2.51 MiB of 3 MiB).

## 2026-10-25: Idle sign-out

39. **Idle sign-out = 15 minutes, 30-second warning, same for owner and staff.** 10 minutes is too short between customers on a busy day, and one rule is simpler than per-role special cases. Pure timing in `lib/idle.ts` (`IDLE_MS`, `WARN_MS`, `isIdle`, `isWarning`, `secondsLeft`); the browser part is `components/IdleGuard.tsx`, mounted in `app/(app)/layout.tsx` only for users that have a role (not on `/login`, not on "No access").
40. **This is a browser-side convenience, not a security boundary.** It protects a phone or PC left open, but someone who copied the login cookie is not stopped, and a closed tab cannot sign itself out (the check runs when the app is reopened). Hard server-side enforcement needs the Supabase Pro "inactivity timeout" setting, which is paid and not used.
41. **The real clock decides, not timers.** The last-activity time is a `Date.now()` value kept in memory and in `localStorage` (key `idle:lastActive`; blocked storage just falls back to memory). It is compared on a 15 s interval (1 s while the warning shows) and on `focus`, `pageshow` and `visibilitychange`, because timers freeze while a phone sleeps. If the limit already passed when the app is reopened, it signs out at once with no warning. Other tabs share the timestamp through the `storage` event, so activity in one tab keeps the others alive. Taps, keys, touches and scrolls count as activity (throttled to once a second).
42. **While the warning shows only "Stay signed in" counts**, so a stray tap or scroll cannot dismiss it, and a tap on the button cannot fall through to the page under it. Sign-out goes through a new `idleLogout` server action, which redirects to `/login?reason=idle`. The login page (now a server component; the form moved to `LoginForm.tsx`) shows the fixed notice only when `reason` is exactly `idle`; nothing from the URL is rendered. Not seen in a browser: no owner login was available when this was built.

## 2026-10-25: Import shows the chosen file

47. **The file name is shown three times on purpose:** in a "File" card the moment a PDF is picked (before the slow reading starts), in a confirm sentence directly above the Import button ("Importing 56 codes from 3HRS_10202026.pdf into 3HRS WIFI"), and in the result ("Imported 56 from 3HRS_10202026.pdf into 3HRS WIFI. Already had 0. Invalid 0."). Pasted text shows "Pasted text". Names are rendered as plain React text, cut in the middle past 60 characters (full name in the card's `title`), so a long name never pushes the Import button off screen.
48. **Re-import warning is browser-only and never blocks.** `lib/import-history.ts` remembers the last 50 imported PDFs (name + size + time) in `localStorage` and warns when the same name and size is chosen again, with the Manila date. It is per device and per browser; the database still skips codes it already has. Storage that is blocked or holds junk is treated as "never imported". Only PDFs are remembered, not pasted text.
49. **Not done on purpose:** no guessing or checking the plan from the file name (a soft "name doesn't match plan" note would fire constantly because the owner's plans and Omada file names are free text), and no page count (needs `extractPdfText` to return more than text, for little value).
50. **Layout check:** a temporary fixture page (deleted before commit) rendered the real component at 390x844 with the sample PDF through the OCR path: file card, confirm sentence and duplicate warning all read clearly. The logged-in page itself was not seen.

51. **Home = "Menu grid"** (option 3, chosen by the owner). Three columns on every width: big duration (`1h`, `10h`, `30m`, `1h 30m`, `2d`; `lib/duration.ts`) with a small unit, plan name small (2-line clamp, full name in `title` and the accessible label), price in a green pill, stock badge on top. Low stock = amber border + warning icon + "N left"; 0 stock = dashed grey tile + "Sold out" badge, not tappable. Colour is never the only signal. The old `.tile` class was removed; new shared classes `.menu*` and five tokens (`--color-low-*`, `--color-off*`) live in `globals.css`.
52. **Odd tile counts** (4, 7 plans) leave empty cells in the last row; tiles keep one size so the grid never looks stretched. Hero text shrinks (`data-long`) for mixed labels like `1h 30m`.
53. **Sales date picker fix:** native date inputs have an intrinsic width (worst on iOS) that pushed the 2-column filter past a 360 px screen. `.date-field` sets `min-width:0; width:100%; appearance:none` and each input sits in a `min-w-0` label with a visible "From"/"To" caption. Measured with a fixture in Chromium and WebKit at 360x740 and 390x844: no horizontal overflow, both fields side by side, 48 px tall.
54. **Short dates:** list rows use `shortManilaTime` ("Today 3:42 PM", "Yesterday 9:05 AM", "Oct 20 · 3:42 PM", year only when not this year); totals use `shortPeriod` ("Oct 25", "Oct 2026"); the sale and group detail pages use the same short form. The receipt keeps its full date (it is a document). Filter and total semantics are unchanged.
55. **Quick ranges** (Today, 7 days, This month, Last month; `lib/sales-range.ts`) are plain links that set `from`/`to` and keep the plan and grouping. At 360 px they wrap to two rows; accepted because the date fields are the priority and each chip is a 48 px target.

## 2026-10-25: Stage 1 (who sold, staff wording, hardening, activity log)

57. **Scope:** who-sold, "Your ..." wording for staff, migration `0003_hardening_and_audit.sql` (file only, NOT applied to the remote project), the audit log and the owner `/logs` page. No PIN login and no login/idle events (later stages). Log starts empty on day one (no backfill). Only the owner can void (unchanged).
58. **The payments policy "leak" did not reproduce.** The plan said a deactivated staff member could read their own old payments. On the local database with the real `authenticated` role the OLD policy already returned zero rows, because its `exists (select ... from sales)` check runs under the invoker's row-level security and `sales_select` requires an active staff role. `0003` still adds the explicit active-staff check, as defense in depth (a rule that does not depend on a second table's policy). The test (`audit.test.ts`, "staff only see their own sales and payments") passes both before and after 0003, so do not describe the change as a fix for a leak.
59. **`sell_voucher` is retired from signed-in users** (`revoke execute ... from authenticated`). The app never calls it (grep: only the generated types mention it) and `sell_cart` covers a single voucher. The concurrency tests call it as the database owner, so they are unaffected.
60. **Audit design:** `public.audit_log` (append-only: a trigger raises on UPDATE, DELETE and TRUNCATE; owner-only SELECT; no insert/update/delete grants; written only by `SECURITY DEFINER` trigger functions through `audit_write`, `search_path=''`, execute revoked from everyone). A database admin can still drop the trigger; this guards against staff and app bugs, not against the database owner. Actor is `auth.uid()`; with no signed-in user (SQL editor) the actor is null and the name is "database admin". Fail-closed: if a log insert ever failed it would roll back the sale; detail sizes are bounded (check <= 4000 chars; plan names <= 60, reason <= 200, <= 10 masked codes), so this should not happen.
61. **One entry per cart.** A deferred constraint trigger on `sales` (`when seq is null or seq = 1`) fires at commit, when every row of the group exists, and aggregates the group (count, total, plan counts, masked codes). One 'sale' entry per cart, per-code 'void' entries. Retries (same key) and failed sales insert no rows, so they log nothing. Single legacy rows (no group) log themselves.
62. **Privacy of the log:** sold and voided codes are masked to `***` + last 3 digits; unsold codes and guest names are never written; imports log the count and plan only. Tested by searching the whole log for every code of the test plans.
63. **Who sold:** owner-only. Names come from `public.profiles` with one `.in('user_id', ids)` query per page (`lib/seller.ts`), fallback "User ab12". Staff see only their own sales, so they get no extra names. The CSV has a `seller` column. Staff totals read "Your sales today / this month / your total" (`lib/labels.ts`), the owner keeps "Today / This month / Total".
64. **Logs page:** `/logs`, owner only (404 for staff). Compact filters like Sales (quick ranges, From/To side by side, person, event type), 50 per page, plain sentences from the pure `describeEvent` (`lib/audit.ts`), "Today by person" from the first 1000 of today's sales (shortcut: upgrade to an RPC if a day ever exceeds that). If `audit_log` does not exist yet (0003 not applied) the page says the log is not switched on instead of crashing.
65. **Nav:** `Logs` is a 7th owner item. Measured at 390 and 360 px: items are 51 and 46 px wide and no label is clipped (scrollWidth equals clientWidth), so no compact arrangement was needed. If an 8th item is ever added, move Settings and Logs under one item.
66. **Local RLS tests** (`supabase/tests/audit.test.ts`) run as the REAL `authenticated` and `anon` roles (`SET LOCAL ROLE` plus JWT claims), unlike the older suites that connect as the database owner. `local-shim.sql` now grants those roles `usage` on schema `auth` and `execute` on `auth.uid()`, as real Supabase does (policies call it directly). Mutation checks: dropping the append-only trigger, opening the SELECT policy and logging every cart row were each caught by a failing test.
67. **Not verified:** the logged-in `/logs`, Sales and Home screens on real data (no owner login for the builder; screenshots were of a deleted sample-data fixture, checked on a production build at 390x844 and 360x740). The e2e tests for `/logs` run only with `E2E_EMAIL`/`E2E_PASSWORD` (staff 404 test also needs `E2E_STAFF_EMAIL`/`E2E_STAFF_PASSWORD`). The local database is a stand-in for Supabase (no PostgREST, no pooler).

## 2026-10-25: Stage 2 (session events)

68. **Session events:** `0004_record_event.sql` widens the `audit_log.action` check with `login`, `logout`, `idle_signout`, `csv_export` and adds `record_event(p_action, p_detail)`: definer, `authenticated` only (anon denied), active owner or staff only, fixed allow-list, detail capped at 300 characters, and at most 60 session events per person per hour (extra ones are dropped quietly, never an error, so a full quota cannot block a sign-out).
69. **App side:** `lib/record-event.ts` swallows every error on purpose: a log failure must never block sign-in, sign-out or the CSV download. Sign-in is logged only after the password is accepted; failed attempts are not logged (that needs the PIN stage and its lockout, so the log cannot be flooded). Idle sign-out is logged before `signOut`, while the session still exists.
70. **Verified on a real Postgres 18 (embedded, no Docker):** all four DB suites pass together, 34 tests, including `0003` (first run against a real engine in this repo) and `0004`. Migrations `0003` and `0004` are still NOT applied to the remote project; apply in order, then deploy.

## 2026-10-25: Stage 3 (v1a, staff PIN sign-in)

71. **Scope built:** plan tasks 11 to 14 for STAFF only. `0005_user_pins.sql`: `user_pins` (bcrypt via pgcrypto, no grant and no policy for anyone, not even service_role), `set_user_pin` and `unlock_user_pin` and `user_pin_status` and `set_staff_active` (owner only), `user_pin_verify` (service_role only, row lock, never raises for a wrong PIN so the count is saved). Staff PIN is 6 digits, 5 tries then 15 minutes, a second lockout within 24 hours is a hard lock until the owner unlocks. `lib/pin.ts` and `lib/lockout.ts` hold the same rules as pure code; the SQL and the pure rules are tested separately against the same scenarios.
72. **Owner PIN is NOT built (v1b).** `set_user_pin` refuses a target with role owner, and `user_pin_verify` fails for any non-staff, so no owner PIN can exist until `0006` (full-owner gating) is written and the spike proves the session method list. The owner keeps email and password through "Use email and password instead".
73. **`pinLogin` is unproven end to end.** The step "generateLink then verifyOtp creates a normal session that `getClaims()` accepts on Cloudflare" is plan task 10 (the spike) and has NOT been run: it needs a throwaway Auth user and the `SUPABASE_SECRET_KEY` secret.
